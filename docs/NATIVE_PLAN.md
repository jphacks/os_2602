# 次の段階の計画（ネイティブ化ほか）

Hack Day のあとに dether を育てるときの方針です。**まだ何も作っていませんし、やるかどうかも未定です。**

dether は JPHACKS 2026 のためのプロダクトです。10/17〜18 の Hack Day（予選）を終え、
**10/30 の結果発表で決勝に出るチームが決まります。** 決勝に進めたら、約2週間でこの紙の内容を作ります。

## 優先順位

どれも必須ですが、順調にいくとは限らないので、**上から作り、詰まったら下から削ります。**

| 順 | やること | 章 |
|---|---|---|
| 0 | **PWA**（ホーム画面に追加して使える）。小さいので最初に入れる | [0](#0-pwa最初に入れる) |
| 1 | **アカウント機能**（独自のアカウント + Bluesky。あわよくば Google・X）と**マイページの一新** | [1](#1-アカウント機能とマイページ) |
| 2 | **アーカイブ**：月ごとにマップをリセットし、前の月はアーカイブへ。アーカイブのページと運営の管理画面は Web から見られる | [2](#2-月ごとのリセットとアーカイブ) |
| 3 | **UX**：画面の切り替えをなめらかにする | [3](#3-画面の切り替えux) |
| 4 | **ネイティブアプリ化**（iOS） | [4](#4-ネイティブアプリ化) |

1〜3 はどれも Web 側の作業なので、PWA でもアプリでも無駄になりません。

**いまの作り**：Django が画面と JSON の API を返す。アカウントは**見えないアカウント**（`main/middleware.py`。初回アクセスで自動で作ってログイン）。
ログインは Cookie のセッション + CSRF。測定は `getUserMedia`、地図は Google Maps JS。
ホーム画面用は `apple-touch-icon` と `theme-color` だけで、**manifest と Service Worker は無い。**

## 0. PWA（最初に入れる）

ネイティブ化がだめになってから作るのでは遅いので、**決勝が決まったらまず入れる**（約1〜2人日）。

- `manifest.webmanifest`（名前・アイコン 192 / 512px・`display: "standalone"`・`start_url`・`theme_color`）を作り、`base.html` から読む
- iPhone 用の設定（`apple-mobile-web-app-title` など）と、切り欠きの対策（`viewport-fit=cover`・`env(safe-area-inset-*)`）
- 自前の戻るボタン（ホーム画面から開くとブラウザの「戻る」が無い）
- 「共有 → ホーム画面に追加」の案内画面（iPhone にはインストールボタンが出ない）
- Service Worker は任意

**注意**：Safari とホーム画面のアプリは **Cookie が別々**で、追加すると見えないアカウントが新しく作られる。
アカウント機能でログインすれば同じ記録が見られるので、案内画面で先にログインを促す。
ホーム画面から開いたときのマイクの許可と、外部ログインから戻ったときの状態は iPhone で確かめる。

## 1. アカウント機能とマイページ

| ログイン方法 | 優先度 | 作り方 |
|---|---|---|
| メールアドレス + パスワード | **必須** | django-allauth |
| Bluesky（atproto） | **必須** | 自前（下）。allauth に部品があるかは要確認 |
| Google | あわよくば | allauth（`google`） |
| X | あわよくば | allauth（`twitter_oauth2`）。API の条件・料金を先に確認し、無料でなければ見送る |

- **土台は django-allauth**：登録・パスワード再設定・メール確認・外部ログイン・複数のログイン方法・ログイン制限がそろっている。
  アプリ向けに Cookie の代わりの `X-Session-Token` も使える。Hack Day 前に消した `accounts` アプリ（`fa00ec5`）は戻さない。
- **見えないアカウントからの引き継ぎ**：登録・初めての外部ログインでは新しいユーザーを作らず、**今の見えないアカウントを本登録に変える**
  （記録は動かさない）。allauth の標準とは違うので、adapter で手を入れる。
- **メール**：Amazon SES。最初は登録したアドレスにしか送れず、本番の申請に数日かかるので早めに出す。DNS に SPF・DKIM を足す。

### Bluesky：Django がトークンを預かる（BFF 型）

```text
アプリ / ブラウザ ──(セッション)── Django ──(OAuth + DPoP)── ユーザーの PDS（Bluesky など）
```

- 仕様（<https://atproto.com/specs/oauth>）：client metadata の JSON を公開（`client_id` はその URL）、DPoP 必須、PAR・PKCE、`scope` に `atproto`。
  confidential client なら `private_key_jwt` と公開鍵（`ES256`）。
- 公式のライブラリは TypeScript（`@atproto/oauth-client-node`）。**Python で足りなければ、OAuth の部分だけ Node の小さなサービスに分ける。**
- **本人を見分けるのは DID**（ハンドルは変わる）。DID・ハンドル・PDS の URL と、暗号化したトークン・DPoP の鍵を保存する。

### マイページ

- プロフィール編集（表示名・ひとこと・アイコン。初期値は「静かなフクロウ」。Bluesky の名前とアイコンも選べる）
- アカウントの設定（メール・パスワードの変更、Bluesky・Google・X の連携と解除）
- 今までのバッジ・調査回数・音の図鑑はそのまま。アーカイブができたら「先月取ったバッジ」も
- アイコンは `clean_photo`（`main/api_posts.py`）で EXIF を消す。表示名は長さの上限を決め、管理画面で直せるようにする
- 画面はログインを待たずに、見えないアカウントで先に作れる

## 2. 月ごとのリセットとアーカイブ

- **データは消さず、「どの月を見せるか」で切り替える。** マップの API は今月の記録だけ返し（`measured_at` で絞る）、
  アーカイブのページは同じ API に年月を渡す。**毎月のバッチ処理は要らない。** 集計表は重くなってから。
- 月の境目は**日本時間**（`timezone.localtime`）。
- 50m ルールを月の中で数え直すなら、`show_on_map` の扱いを変える。バッジはマイページには残す。
- 運営の管理画面は、まず Django の `/admin/` を広げる（月ごとの記録数・ユーザー数・投稿の確認と非表示）。
- アカウント機能と関係なく作れるので、1章と並行できる。

---

## 3. 画面の切り替え（UX）

- **View Transitions API** で前後の画面をつなぐ（バッジ一覧 → 詳細、地図のピン → 投稿 など）。非対応の環境ではふつうに切り替える。
- 主な画面の移動は、中身だけ入れ替える形に寄せる。PWA の戻るボタンも同じ動きにそろえる。
- `prefers-reduced-motion` の人には動きを控える。触覚フィードバックはネイティブ化できたときだけ。
- 2週間なら、**いちばん見せたい動線1〜2本**に絞る。

## 4. ネイティブアプリ化

- **Capacitor で今の Web 画面を包む。** Swift / Kotlin などでの作り直しはしない。
- **リリースは iOS のみ。** Google Play は個人だと「12人以上が14日間テスト」が要るため、Android は後から。
- **Mac がないので、ビルドと署名は Codemagic（無料枠あり）に任せる。** 代わりは GitHub Actions の macOS ランナー、クラウドの Mac。
  署名の鍵・API キーはリポジトリに入れず Secrets に置く。
- **全員 iPhone**：日々の確認は Safari で Web 版。マイクの許可・アプリへの戻り・触覚など、アプリならではの部分だけ TestFlight で
  （1回のビルドに10〜20分）。Mac がないと Web インスペクターが使えず、アプリ内だけの不具合は追いにくい。
- **アプリ内のログイン**：ブラウザで開いたログインの Cookie はアプリに届かない。ログイン後に Django が使い捨ての合言葉を作り、
  `dether://login?code=...` でアプリに戻して、セッション（または `X-Session-Token`）と交換する。
- **配り方**：TestFlight 内部テスト（チーム内・審査なし）→ 外部テスト（公開リンク・初回だけ半日〜1日の審査）→ App Store（9割が48時間以内）。
  **App Store まで出すかは未定。** TestFlight までなら、4.2（Web を包んだだけ）・5.1.1(v)（アプリ内のアカウント削除）・
  4.8（外部ログインの決まり）の対応と、ストアの掲載情報を後回しにできる。
- **費用**：Apple Developer Program は年1万3千円前後（6人で割れば1人2千円ちょっと）。ビルドする直前に登録すればよい（確認に1〜2日）。
- その他：機種でマイクの感度が違う。Google Maps の API キーの制限を見直す。

## 2週間の進め方（決勝に進めたら）

完璧は目指さず、**動くものを見せられるところまで**。

**10/30 までに（無料・決勝に進めなくても損しない）**：Web 版で Bluesky ログインを試す（DID が取れるか）/

### 担当と作業量（例。得意なもので入れ替える）

1人が使える時間は 46〜56時間（平日2〜3時間 × 10日 + 休日6〜7時間 × 4日）。

| 担当 | やること | 作業量 | AI ツール |
|---|---|---|---|
| A | 優先1：Bluesky のログイン | 4〜7人日（26〜46時間）。**上振れすると持ち時間ぎりぎり** | Claude Code |
| B | 優先1：マイページの連携部分・A の手伝い（ネイティブ化ならアプリへの受け渡しも） | 2〜3人日 + 手伝い | なし |
| C | 優先1：独自のアカウント（allauth・引き継ぎ・SES）・あわよくば Google・X | 4〜6人日 | Claude Code |
| D | 優先2：アーカイブのページ・運営の管理画面 | 4〜5人日 | Codex |
| E | 優先1：マイページの画面 → 優先3：UX | 3〜5人日 | Copilot |
| F | 優先0：PWA → 優先4：Capacitor・TestFlight → テスト・デモ・発表 | 3〜6人日 + テスト | なし |
| | **合計** | **20〜32人日（約130〜210時間）**。テスト・手戻りは含まない | |

- 「人日」は1人が集中して約6.5時間の作業量。**全員分を足した量で、カレンダーの日数ではない**（6人で割ると1人あたり約22〜35時間）。
- **AI が効くのはコードを書く部分だけ**（allauth・管理画面・API・manifest・画面）。Bluesky は仕様が新しく半分くらい。
  署名・実機確認・申請待ちは効かない。効けば 16〜24人日くらいになるが、**計画は多めの見積もりのまま**にする。

### AI で同時に書くときの注意

- 共通の決まり（コメントの書き方・役割分担・`.env` は読まない など）を、`CLAUDE.md`・`AGENTS.md`・`.github/copilot-instructions.md` に同じ内容で置く（今は無い）。
- `config/settings.py`・`main/models.py`・`templates/base.html` は衝突しやすいので、変える前に声をかける。
- ログインまわりは、マージ前に別の人がレビューする。各ツールで `.env` や鍵ファイルを読まない設定にする。

### 区切り

- **1週目の休日が終わるまでに、Web 版で Bluesky ログインして DID が取れていること。** だめなら Node の公式ライブラリに切り替える。
- **2週目の頭に、優先4に進めるか判断する。** 1〜3 が遅れていれば、ネイティブ化はやめて PWA のまま出し、F は 1〜3 を手伝う。

**後回しにするもの**：Google・X（余裕がなければ）/ 測定のネイティブ化・機種ごとの補正 / 月ごとの集計表 / Bluesky 以外の PDS /
Bluesky への投稿 / 全画面の演出 / 専用の運営画面 / Android 版 / App Store への申請

## バックアップ案：PWA のまま配る

ネイティブ化がだめなときは、最初に入れた PWA のまま、**追加の作業なしで**「ホーム画面に追加」してもらう。
